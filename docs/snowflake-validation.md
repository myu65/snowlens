# 接続したSnowflakeでの検証

2026年10月6日にテストアカウントで確認しました。Snowflakeは10.35.101、接続先はAWS_AP_NORTHEAST_1、CLIは3.28.0です。PAT接続は、接続元を許可したネットワークポリシーの設定後に成功しました。認証情報、ユーザー名、本人ID、実データはこの記録に含めません。

## SQLを直接実行して確認した内容

setup.sql、private-state.sql、dataset-state.sqlを実行し、表・Secure Function・行ポリシー・保存プロシージャの作成に成功しました。通常の表とスキーマをSYSADMINの管理下に置き、本人確認と保存処理の所有者を専用のロールに分けました。処理所有者には業務ソースのSELECTや公開権限を付けていません。

合成テストユーザーを作り、キー認証で別々のSQLセッションから12項目を確認しました。2人の個人保存を試すときは、同じ閲覧ロールを使い、secondary rolesをNONEにしました。個人ごとのロールは作っていません。

| 確認対象                   | 確認結果                                                                 |
| -------------------------- | ------------------------------------------------------------------------ |
| テストユーザーと共通ロール | 異なるユーザーで同じ閲覧ロールを使用できた                               |
| 未登録の本人               | 本人IDはNULLになり、個人の保存を拒否した                                 |
| 本人の識別                 | 2人を別の変更しないIDとして取得できた                                    |
| 同じIDの個人入力           | 各ユーザーが自分の1行だけを読み、入力中の偽のownerを所有者に使わなかった |
| 保存表・本人対応の直接更新 | 一般利用者の直接DMLと対応表の変更を拒否した                              |
| 古い版の編集・削除         | 新しい版を保ち、古い版の操作を拒否した                                   |
| ロールの切り替え           | 閲覧・編集ロールを切り替えても本人IDと個人保存を保った                   |
| Dataset編集                | 閲覧者の保存と、別の編集者による所有者の上書きを拒否した                 |
| 不正な本人対応             | 重複・無効な対応、同じIDの複数割り当てで本人IDをNULLにした               |
| ユーザー名の変更           | 同じ本人IDへ対応を更新して、自分の保存を引き継げた                       |
| ユーザー名の再利用         | 新しいユーザーには新しいIDを登録し、以前の保存を見せなかった             |
| 処理所有者の権限           | 本人対応・定義保存の権限だけを持ち、業務SELECTや公開権限を持たなかった   |

入力は合成データです。終了後に個人入力、お気に入り、テストDataset、本人の対応、テストユーザーを削除しました。キーの秘密部分はファイルに保存していません。保存処理や行ポリシーを外して検証に合わせる変更は行っていません。

## App Runtimeでまだ確認できない内容

`snow app validate`は成功し、コードのアップロードとartifact repositoryの作成まで進みました。サーバー側のビルド開始時に、Snowflakeが次の理由でデプロイを拒否しました。

```text
395054: Snowpark Container Services feature SNOWFLAKE APP RUNTIME not available for trial accounts
```

Application Serviceは起動していません。通常アカウントでのデプロイと、trusted ingressを通す2ユーザーの検証が必要です。SQLの直接実行では、Runtimeのservice tokenとcaller tokenの合成、caller grantとの制限、偽のヘッダーの拒否を確認できません。

4種類のソースと行・マスキングポリシー、元データの権限撤回、結合、セマンティック指標、公開SQL、クエリのキャンセル、同時更新の確認もApp Runtimeでは未実施です。[Runtimeの検証手順](runtime-validation.md)を通るまでIssue #5を残します。

Excel・CSVの変更を含むプロダクションビルドで、lint、型検査、68件の単体テスト、18件のPlaywrightテストが成功しました。PCと390px幅のダウンロード操作、実際のExcelファイルの再読み込み、テーブル定義、型、条件、総計を確認しています。これらはmockと生成ファイルの確認で、Snowflakeのcaller権限の証拠には使いません。
